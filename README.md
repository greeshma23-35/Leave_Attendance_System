# Employee Leave & Attendance Management System

A Django + Django REST Framework application with a simple server-rendered web UI for employee attendance and leave management.

## What was added/changed

- Django template frontend under `templates/` with responsive CSS/JS under `static/`.
- Session-based web login at `/login/` while the existing JWT API remains available under `/api/auth/`.
- Role-aware dashboard for Employee, Manager and Admin.
- **Admin UI:** can create Managers and Employees from `People -> Add person`.
- **Manager UI:** can create Employees only; the new employee is automatically assigned to that manager.
- Employees cannot create users or change their role/manager through the web UI.
- Employees can check in/out, apply for leave and cancel pending requests.
- Managers/Admins can review applicable pending leave requests.
- Managers/Admins can view team attendance; API permissions remain enforced.
- Neon/PostgreSQL support through `DATABASE_URL` with SSL required.
- WhiteNoise for static files on Render; Nginx remains available for Docker/local deployments.
- `build.sh` runs migrations and `collectstatic` for Render.
- `render.yaml` provides a Render Web Service blueprint.
- `/health/` provides a lightweight health check.

## Roles

| Role | Web UI capabilities |
|---|---|
| Employee | Dashboard, check-in/out, own attendance, apply/cancel leave |
| Manager | Employee capabilities + team attendance/leave + add employees + approve/reject direct-report leave |
| Admin | Manager capabilities + organization-wide people/leave/attendance + add managers and employees + Django admin |

## Local setup

```bash
python -m venv venv
# Windows
venv\\Scripts\\activate
# macOS/Linux
# source venv/bin/activate

pip install -r requirements.txt
copy .env.example .env   # Windows
# cp .env.example .env   # macOS/Linux

python manage.py makemigrations accounts attendance leaves
python manage.py migrate
python manage.py createsuperuser
python manage.py runserver
```

Open `http://127.0.0.1:8000/login/`.

If `DATABASE_URL` is empty, the project falls back to SQLite for local development. To use Neon locally, set `DATABASE_URL` to your Neon pooled/direct PostgreSQL connection string.

## Neon database

Set this environment variable:

```env
DATABASE_URL=postgresql://USER:PASSWORD@HOST/DBNAME?sslmode=require
```

The settings parse `DATABASE_URL` and require SSL. Do not commit the real Neon connection string.

After connecting a new Neon database:

```bash
python manage.py makemigrations accounts attendance leaves
python manage.py migrate
python manage.py createsuperuser
```

## Render deployment

Recommended approach: deploy the Django app as a **Python Web Service** from the Git repository and use Neon as the external PostgreSQL database.

Render configuration included in `render.yaml`:

- Build: `./build.sh`
- Start: `gunicorn config.wsgi:application --workers 2 --threads 4 --timeout 120`
- Health check: `/health/`
- `DEBUG=False`
- `SECRET_KEY` generated by Render
- `DATABASE_URL` marked as a secret/sync-disabled value so you enter the Neon URL in Render

### Manual Render steps

1. Push this project to GitHub/GitLab.
2. In Render, create a new **Web Service** and select the repository.
3. Use Python runtime.
4. Set build command to `./build.sh`.
5. Set start command to `gunicorn config.wsgi:application --workers 2 --threads 4 --timeout 120`.
6. Add environment variable `DATABASE_URL` with the Neon connection string.
7. Set `SECRET_KEY` to a generated secret if you are not using the Blueprint's generated value.
8. Set `DEBUG=False`.
9. Set `CSRF_TRUSTED_ORIGINS` to your final Render URL, for example `https://your-service.onrender.com` (the settings also use Render's hostname automatically when available).
10. Deploy.
11. After deployment, open Render Shell and create the first admin:

```bash
python manage.py createsuperuser
```

Then use `/login/` for the custom UI or `/admin/` for Django administration.

## API

The original REST API remains available:

- `/api/auth/token/`
- `/api/auth/token/refresh/`
- `/api/auth/me/`
- `/api/auth/users/`
- `/api/attendance/`
- `/api/leaves/` and related leave endpoints
- `/api/docs/`

## Docker

The Dockerfile remains available for containerized deployment. For a single Render Web Service using the Python runtime, the included WhiteNoise setup is simpler because Render can serve collected static assets directly from Django. Nginx remains useful for a VM/docker-compose architecture.

## Important production notes

- Never commit `.env` or real credentials.
- Use a strong generated `SECRET_KEY` in production.
- Keep `DEBUG=False` in production.
- Configure a custom domain and its HTTPS origin in `CSRF_TRUSTED_ORIGINS` when applicable.
- Back up Neon data according to your operational requirements.
- The free Render service may sleep when idle; this can make the first request after inactivity slower.
